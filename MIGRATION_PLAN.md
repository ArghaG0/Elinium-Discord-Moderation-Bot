# Elinium migration plan

Last updated: 2026-10-02.

## Context

Elinium is a Python Discord bot built with discord.py and cogs. It is migrating from local JSON storage to PostgreSQL hosted on Neon (serverless), with the eventual goal of reliable 24/7 hosting. Dependency management will also move to `uv`.

**Start fresh in PostgreSQL. Do not import old JSON data or create an import script.** Existing JSON files remain in use until their consumers are migrated and Phase 6 removes them.

`main.py` creates the bot, initializes the database, and loads `cogs/general.py` and `cogs/moderation.py`. `config.py` validates startup environment configuration. `db/` contains asynchronous PostgreSQL helpers. `utils.py` still contains legacy JSON helpers, moderation-log rendering, duration parsing, and the unchanged Phase 1 schema initialization. Modlog and confession settings now use PostgreSQL. Warnings and blacklists still use JSON pending Phases 4 and 5.

## Agreed file organization and scope

- Keep `main.py`, `utils.py`, `README.md`, and this plan at the root. Keep the two existing cogs and their command organization unchanged during this phase.
- Database access lives in `db/settings.py`, `db/warnings.py`, and `db/blacklists.py`, with `db/__init__.py` identifying the package. This supersedes the original proposal to add Phase 2 helpers to `utils.py`.
- Validated deployment configuration lives in root-level `config.py`; `.env.example` contains placeholders only. Loading `.env` happens at explicit startup, not import time.
- Keep automated checks in `tests/`. Additional documentation and maintained one-off tools may later go in `docs/` and `scripts/`, but do not create empty folders.
- Keep `requirements.txt` at the root during the dependency transition. Future `pyproject.toml` and `uv.lock` also belong at the root; their creation remains a separate task.
- Keep the four JSON files at the root until Phase 6, leave `utils.py` unchanged in Phase 2, and retain `discloud.config` pending an owner decision.
- Generated bytecode is disposable and ignored. Both existing `__pycache__/` directories, including orphaned `keep_alive` bytecode, were removed. `.gitignore` now explicitly ignores `.venv/` and uses separate comment lines for `.DS_Store` and `Thumbs.db`.
- Cog splitting, centralized command-error handling, moving schema initialization, pool lifecycle refactoring, and the `on_ready` synchronization change remain deferred. Phase 2 logging establishes startup/application console logging; existing cog and legacy-helper `print()` calls remain for later cleanup.

## Current schema

The following matches `utils.py:init_db()` as of the last update. The statements run through an acquired pool connection, sequentially, without an explicit enclosing transaction.

```sql
CREATE TABLE IF NOT EXISTS guild_settings (
    guild_id BIGINT PRIMARY KEY,
    modlog_channel_id BIGINT,
    confession_channel_id BIGINT
);

CREATE TABLE IF NOT EXISTS warnings (
    id SERIAL PRIMARY KEY,
    guild_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    moderator_id BIGINT NOT NULL,
    reason TEXT,
    timestamp TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_warnings_guild_user
    ON warnings (guild_id, user_id);

CREATE TABLE IF NOT EXISTS blacklisted_words (
    id SERIAL PRIMARY KEY,
    guild_id BIGINT NOT NULL,
    word VARCHAR(255) NOT NULL,
    UNIQUE (guild_id, word)
);
CREATE INDEX IF NOT EXISTS idx_blacklisted_words_guild
    ON blacklisted_words (guild_id);

CREATE TABLE IF NOT EXISTS blacklisted_links (
    id SERIAL PRIMARY KEY,
    guild_id BIGINT NOT NULL,
    link VARCHAR(255) NOT NULL,
    UNIQUE (guild_id, link)
);
CREATE INDEX IF NOT EXISTS idx_blacklisted_links_guild
    ON blacklisted_links (guild_id);
```

Primary keys and unique constraints also create their supporting indexes. There are no foreign keys or additional check constraints. Channel IDs, warning reasons, and warning timestamps are nullable; the timestamp default does not impose `NOT NULL`. `CREATE TABLE IF NOT EXISTS` does not upgrade existing table definitions.

### Phase 2: Async DB helpers and approved startup preparation

**Status: DONE; verified and approved by owner.** The owner amended the original scope to use `db/` and explicitly included `config.py` validation, an import-safe `main.py` entry point, and logging setup. No cog was switched to PostgreSQL during Phase 2.

Implemented asynchronous helpers using the existing pool and parameterized SQL for all four data categories:

- Guild settings: read, set, and clear modlog/confession channel settings as needed. Updating or clearing one setting must preserve the other column.
- Warnings: add, fetch in deterministic order, count, and delete all, a selected warning, or the latest N warnings within a guild/user scope. Keep database IDs distinct from displayed 1-based warning numbers.
- Blacklisted words and links: read, add, and remove guild-scoped entries, including the reads needed to populate the later cache. Handle duplicate entries consistently with the unique constraints and account for the 255-character limits.

Helpers accept an `asyncpg.Pool` and integer Discord IDs. They do not import Discord or send messages. Database exceptions propagate rather than becoming empty results. Typed result records preserve nullable schema fields and timezone-aware database timestamps.

| Module | Public API and contract |
| --- | --- |
| `db/settings.py` | `get_settings` returns `GuildSettings`; an absent row means both channels are unset. `set_modlog_channel` and `set_confession_channel` accept an ID or `None` to clear, return updated settings, and atomically preserve the other column. |
| `db/warnings.py` | `add_warning` returns a `Warning`; `get_warnings` returns oldest-first rows ordered by database ID; `count_warnings` returns an integer. `delete_warning` deletes by database ID within the guild/user scope and returns the removed record or `None`. |
| `db/warnings.py` | `clear_warnings(pool, guild_id, user_id, num_or_index=None)` clears all for `None`, one current 1-based display position for a positive integer, or the latest N for a negative integer. Returns deleted records oldest first for logging. Zero raises `ValueError`; non-integers raise `TypeError`; out-of-range positions/counts raise `IndexError` without deleting anything. Clearing all from an empty history returns `[]`. |
| `db/blacklists.py` | `add_word`, `remove_word`, `add_link`, and `remove_link` return whether a row changed. Entries are stripped/lowercased, restricted to 1-255 characters, and reject NUL; blank/invalid-length values raise `ValueError`. Duplicate additions and absent removals return `False`. Command-level splitting remains the caller's job. |
| `db/blacklists.py` | `get_words` and `get_links` return lists in insertion order. `get_all_blacklists` returns one SQL snapshot keyed by integer guild ID, with `blacklisted_words` and `blacklisted_links` lists; guilds with no entries are omitted. This supplies future cache initialization data but does not install a cache. |

Warning mutations use transactions and a deterministic transaction-scoped advisory lock per guild/user. Selection and deletion are atomic among callers of these helpers, and failed operations roll back. Direct SQL writers would need to follow the same lock protocol to share this guarantee. Display positions are resolved at mutation time; use database IDs when stable identity is required. ID ordering avoids ambiguity from equal or nullable timestamps.

Startup additions:

- `load_config()` loads the root `.env` only when called, preserving existing environment values. Required token/database settings and optional owner ID/log level are validated before connections open. Error messages identify settings without their values; the config representation omits credentials.
- `main()` attaches the validated config to `bot.config` and runs the bot only behind `if __name__ == "__main__"`. Importing the module constructs/registers the bot but does not read `.env`, connect, or configure logging.
- Console logging includes time, severity, and logger name. Startup, extension-loading, and slash-sync messages now use the module logger, with tracebacks for unexpected failures. `bot.run(..., log_handler=None)` avoids adding a duplicate Discord handler. Existing lifecycle placement is unchanged.

## Migration and hosting considerations

- PostgreSQL is required for startup and now backs modlog/confession settings. Warnings and blacklist persistence remain JSON-based until their phases.
- There is no explicit database pool shutdown handling yet. Missing/invalid startup configuration, including `DATABASE_URL`, is now validated in `config.py`.
- JSON operations remain synchronous and overwrite whole files; invalid JSON is treated as empty data and may be overwritten by later saves.
- The README currently documents `BOT_TOKEN` and environment-provided emojis, whereas the code reads `DISCORD_TOKEN` and uses hardcoded emojis. It also describes pip and JSON storage.
- Completing these six phases does not itself deploy the bot or establish 24/7 hosting. Hosting setup and operational verification remain separate work.
